# 10. 서버 수집·캐시 구조 실현 가능성 (2026-10-04 분석, 코드 변경 없음)

오너 요청: "서버에서 데이터를 수집해 저장해 두고, 청약 일정이 끝나면 지우고, 앱은 서버에서 받도록. 그러면 API 사용률이
떨어지나? 지금 API로 커버되나? 사용자가 직접 API를 신청하는 건 불편하다. 서버 리소스가 크지 않은 점도 고려해라."

표기: **[확인]** = 직접 조회·측정한 값, **[가정]** = 추정치(근거 함께 적음). 기준 수치는 docs/09에서 가져와 다시 썼습니다.

## 결론 (요약)
- **실현 가능합니다.** data.go.kr 호출은 수집 주기로만 정해지고 사용자 수와 무관합니다. 하루 41~457회로 개발계정 한도
  (오퍼레이션당 40,000/일)의 최대 약 1%입니다. 성수기에 특별공급 신청현황까지 넣어도 약 2%입니다.
- **운영계정은 꼭 필요하지 않고 "있으면 좋은" 수준**입니다. 이용약관에 개발계정으로 공개 서비스를 하지 말라는 조항은
  없습니다. 다만 포털 안내는 운영계정을 "서비스용"이라고 설명하므로, 일반 배포 전에 활용사례를 등록하고 운영계정을
  신청하길 권합니다.
- **서버 부담은 수집 작업 쪽은 무시할 수준**입니다(하루 몇 분 CPU, 메모리 수십 MB, 저장 수 MB 이하). 부담이 되는 것은
  **앱 요청 처리**와 **가용성**입니다. 지금 서버(t3.small, RAM 2GB, 회사 시스템과 공유)가 사용자 요청까지 직접 받는 것은
  권하지 않습니다.
- **추천 구조: "서버는 수집만, 배포는 정적 파일"**입니다.
  - 현재 서버의 cron이 오너 키로 수집합니다. 해외 IP 접근 확인 후에는 GitHub Actions로 옮길 수 있습니다.
  - 수집 결과로 정적 JSON(목록 + 공고별 상세)을 만들어 GitHub Pages(0원)에 올리고, 사용자가 늘면 Cloudflare로 옮깁니다.
  - 앱은 정적 파일만 받고, 마지막으로 받은 데이터를 캐시해 둡니다. docs/09 추천안 B를 서버 제약에 맞게 다듬은 것입니다.

**판단:** 한도 면에서는 개발계정으로 충분하고, 약관상 금지도 없습니다. 운영계정은 "있으면 좋은" 수준입니다. 다만 다음 이유로
**일반 배포(지인 범위 밖, 스토어 등록 등) 전 신청**을 권합니다.
1. 포털이 정한 용도와 맞아 이용 제한 시 다툼 여지가 줄어듭니다.
2. 장애·증설 문의 시 '운영 서비스'로 대응받기 쉽습니다.
3. 나중에 주기를 줄이거나 오퍼레이션을 늘릴 여유가 생깁니다.

**운영계정 신청 절차** (data.go.kr 공통 절차, 서비스마다 각각 신청)
1. 마이페이지 → 데이터 활용 → Open API → 활용신청 현황에서 해당 서비스를 고르고 상세로 들어가 [운영계정 신청]을 누릅니다.
2. **활용사례 등록**이 전제입니다. 서비스명, 설명, 화면 캡처, 접근 URL을 넣습니다.
   - URL은 GitHub 릴리스 페이지나 스토어 주소를 쓰면 됩니다.
   - 화면 캡처는 docs/img의 앱 화면을 쓸 수 있습니다.
3. 필요한 일일 트래픽을 적습니다. 이 구조라면 1,000~5,000이면 충분하고, 여유를 두려면 10,000을 적습니다.
4. 심의승인(제공기관: 한국부동산원)을 거칩니다. 보통 **2~3 영업일**이고 결과는 가입 이메일로 옵니다.
   - [가정] 타 기관 안내 기준이고, 이 기관의 실제 소요 기간은 미확인입니다.
   - 운영단계는 심의승인입니다 [확인, docs/09].
5. 활용기간은 보통 2년이고 마이페이지에서 연장할 수 있습니다 [가정]. 만료되면 수집이 멈추므로 만료일을 꼭 확인하세요.
   개발계정과 운영계정 모두 해당됩니다.

## c. 서버 리소스
### 측정한 값 [확인] — 이 회사 시스템이 도는 호스트 (2026-10-04)
| 항목 | 값 |
|---|---|
| 인스턴스 | AWS EC2 **t3.small**, 서울 리전(ap-northeast-2) |
| CPU | 2 vCPU (Xeon 8259CL). t3는 버스터블이라 기준 성능이 vCPU당 20%이고, 크레딧이 다 떨어지면 그 수준으로 제한됨 |
| 메모리 | 1.9GB + 스왑 6GB. 평소 사용 0.7~1.5GB(회사 에이전트들). 측정 중 여유가 90MB까지 떨어짐. 같은 날 안드로이드 빌드가 메모리 부족으로 두 번 죽음 |
| 디스크 | 48GB 중 22GB 남음 |
| 네트워크 | api.odcloud.kr 응답 0.14초. 같은 날 06시대 DNS 일시 장애로 에이전트 턴 3회 실패 |
| 대역폭·요금 | 측정 안 함. EC2 인터넷 송신은 월 100GB 무료, 그 뒤 서울 기준 약 $0.126/GB [가정, AWS 요금표 기준·재확인 필요] |

"현재 서버"가 이 호스트가 아니라 오너의 다른 서버라면 그 사양으로 다시 계산해야 합니다. 이 문서는 이 호스트를 기준으로 합니다.

### 수집 작업 부하 [가정, 근거 포함]
- 호출 하루 100~900회 × 응답 1~30KB. 수신량은 하루 수 MB 이하입니다.
- Python 스크립트 1회 실행은 수 초에 메모리 약 30~50MB입니다. cron으로 돌고 끝나면 내려가므로 상주 메모리가 없습니다.
- t3 CPU 크레딧 소모는 무시할 수준입니다.

### 저장 용량 [가정]
- 공고 1건 ≈ 20KB입니다(현재 앱 Room 필드 수 기준).
  - 공고 1.2KB
  - 주택형 약 8개 × 0.5KB = 4KB
  - 경쟁률 8형 × 1·2순위 × 거주구분 3 ≈ 48행 × 0.25KB = 12KB
  - 특공현황 3KB
- 삭제 정책을 적용하면 보관 중인 공고는 약 60~110건(전국 하루 약 1건 × 보관 60~120일)입니다. 원본은 **1~2.2MB**, gzip으로는 0.1~0.3MB입니다.
- 삭제하지 않아도 1년에 약 330건, 7MB입니다. 즉 삭제는 **용량 때문이 아니라 데이터 정리와 정책 때문**에 필요합니다.

### 앱 요청 처리 부하 [가정]
배포 파일은 둘로 나눕니다.
- `index.json`: 보관 중인 전 공고의 요약 + 분양가·경쟁률 요약. 약 150KB, gzip 약 25KB.
- `n/<공고ID>.json`: 상세(주택형·경쟁률 전체). 약 20KB, gzip 약 3KB.

앱은 하루 6번(백그라운드 4회 + 수동 2회) index를 받습니다. 바뀌지 않았으면 ETag 304(약 0.5KB)가 오고, 절반은 새 내용이라고 가정합니다.
상세는 하루 3건을 엽니다. 이렇게 하면 1인당 하루 약 90KB, **월 약 2.7MB**입니다.

| 사용자 | 요청/일 | 평균 rps | 피크 rps (평균 × 10) | 송신/월 | 파일 하나 통째(분할·ETag 없음, 200KB × 6) |
|---|---|---|---|---|---|
| 1천 | 9천 | 0.1 | 1 | **2.7GB** | 36GB |
| 1만 | 9만 | 1 | 10 | **27GB** | 360GB |
| 10만 | 90만 | 10 | 100 | **270GB** | 3.6TB |

- 피크를 평균의 10배로 잡은 것은 접수일 아침에 수동 확인이 몰리는 경우입니다. WorkManager 주기 실행은 기기마다 시각이 흩어집니다.
- 파일을 나누고 ETag/304·gzip을 쓰면 트래픽이 약 13분의 1로 줄어듭니다. 이것이 서버 부담을 가르는 핵심 설계입니다.

## d. 앱 요청을 누가 받나 — 비교
| | (i) 자체 서버가 API로 응답 | (ii-a) 정적 JSON → GitHub Pages | (ii-b) 정적 JSON → Cloudflare Pages/R2 |
|---|---|---|---|
| 서버가 사용자 요청 처리 | 함(상시 가동 필수) | 안 함 | 안 함 |
| 지금 서버(t3.small)에 주는 부담 | API 프로세스와 DB 상주 100~200MB, TLS 처리 CPU. 1만 명 피크 10 rps는 가능하나 10만 명 100 rps면 CPU 크레딧이 빠듯. RAM 2GB를 회사 시스템과 나눠 써서 빌드와 겹치면 OOM 위험 | 수집 cron뿐 | 수집 cron뿐 |
| 비용 | 송신 1만 명 0원(무료 100GB 이내), 10만 명 약 $21/월 [가정] | 0원 | 0원(10만 명이면 R2 읽기 초과로 약 $6/월 [가정], Pages는 무제한) |
| 사용자 상한 | 서버 사양·요금만큼 | 권장 대역폭 100GB/월 ÷ 2.7MB ≈ **3.7만 명** (가벼운 제한, 넘으면 GitHub 연락) | 사실상 무제한 |
| 서버 장애 시 | 앱 데이터 갱신 중단 | 배포는 계속 살아 있음. 갱신만 멈춤 | 같음 |
| 추가 준비 | 도메인·TLS 인증서·모니터링 | 별도 저장소(`chungyak-feed`)와 배포 토큰 | Cloudflare 계정. Pages 무료는 월 500회 배포 제한이라 2시간 이상 주기 [가정] |

**docs/09 추천안 B와의 관계:** B는 "GitHub Actions가 수집해 정적 JSON을 GitHub Pages에 배포"였습니다. 이번 구조는 B와 같은 계열이고, 두 가지만 바뀝니다.
1. **수집 위치:** Actions 러너는 미국 IP인데, api.odcloud.kr이 해외 IP를 막는지는 **미확인**입니다. 국내 서버(지금 호스트, 서울)에서 0.14초에 응답하는 것은 확인했습니다.
   그래서 1단계는 **지금 서버의 cron**으로 수집하고, Actions에서 한 번 테스트해 통과하면 Actions로 옮길 수 있습니다(그러면 서버가 아예 필요 없음).
2. **삭제 정책과 파일 분할**을 명시했습니다.

**서버가 계속 켜져 있어야 하나:** (ii) 구조에서는 아닙니다. 수집 cron은 하루 24번 수 초씩 도는 것이 전부이고,
서버가 꺼져 있어도 사용자는 마지막으로 배포된 파일을 계속 받습니다. 정보가 늦어질 뿐 앱은 멈추지 않습니다.

**장애 시 앱 동작(캐시 폴백, 구현 제안):**
1. 앱은 마지막으로 성공한 index와 상세를 기기 DB에 저장합니다. 지금 Room 구조를 그대로 씁니다.
2. index의 `generatedAt`이 6시간 넘게 지났으면 "데이터가 n시간 전 기준입니다" 배너를 띄웁니다.
3. 24시간이 넘었는데 사용자가 개인 키를 넣어 두었다면 지금처럼 data.go.kr을 직접 호출합니다(백업 경로).
   개인 키 입력은 필수에서 선택으로 바뀝니다.
4. 배포 파일을 못 받으면 지금의 지수 백오프로 재시도합니다. 정적 호스팅이라 서버 과부하로 이어지지 않습니다.

## 삭제(보존 기간) 규칙 제안
| 대상 | 규칙 |
|---|---|
| 공고 + 주택형 + 경쟁률 + 특공현황 | **당첨자 발표일 + 30일**이 지나면 삭제. 발표 후 계약 기간(보통 발표 2~3주 뒤)까지 경쟁률·분양가를 볼 수 있게 함 |
| 일정 값이 비었거나 이상한 공고 | 모집공고일 + 120일이 지나면 삭제(안전장치) |
| 정정·취소 공고 | 목록에서 사라진 공고는 7일간 '취소/정정' 표시 후 삭제 |
| 배포 파일 | 매 수집 때 보관 중인 공고만으로 새로 생성. 삭제된 공고의 상세 파일도 같이 지움. 배포 저장소는 이력을 남기지 않는 방식(고아 브랜치 강제 푸시)이라 저장소가 커지지 않음 |
| 앱 기기 DB | index에서 빠진 공고는 기기에서도 같은 규칙으로 정리. 관심 표시 공고만 남길지는 별도 결정 |

## e. 결론
- **실현 가능 여부:** 가능합니다. 호출 수(한도의 약 1%), 저장(수 MB), 수집 부하(무시 가능) 모두 문제없습니다. 제약은 배포 대역폭과 가용성뿐이고, 정적 배포로 해결됩니다.
- **추천 구조 1개:** 지금 서버 cron으로 수집(목록 1시간, 경쟁률 3시간) → 삭제 규칙 적용 → `index.json` + 공고별 상세 JSON 생성
  → 별도 공개 저장소의 GitHub Pages로 배포 → 앱은 정적 파일만 받음(ETag·캐시, 개인 키는 선택 백업).
  사용자가 약 3만 명을 넘으면 같은 파일을 Cloudflare로 옮깁니다(앱의 피드 주소만 바꾸면 되도록 설정값으로 둠).
- **남는 위험**
  - 가용성: 수집 서버(회사 호스트)가 재시작하거나 DNS 장애가 나거나 키가 만료되면 데이터가 늦어집니다.
    → 배너로 표시하고, 수집이 6시간 넘게 실패하면 오너에게 알립니다(리포트·이슈). Actions로 옮기면 호스트 의존이 사라집니다.
  - 키 보호: 키는 서버의 저장소 밖 파일(권한 600, signing 폴더와 같은 방식)이나 Actions 시크릿에만 둡니다.
    배포 JSON에 키가 섞이지 않았는지 검사하는 테스트를 둡니다(NoEmbeddedKeyTest 확장). 공개 저장소·APK·빌드 설정에는 넣지 않습니다.
  - 단일 키 의존: 오너 키가 막히면(약관 판단, 만료) 전 사용자가 갱신을 못 받습니다. 운영계정 신청과 만료일 관리로 줄이고,
    사용자가 원하면 개인 키로 넘어가는 폴백을 남깁니다.
  - 비용: 1만 명까지 0원. 10만 명이면 Cloudflare 기준 0~수천 원/월입니다. 자체 서버로 직접 받으면 약 $21/월 + 서버 증설이 필요할 수 있습니다.
  - 미확인 가정: api.odcloud.kr 해외 IP 허용 여부, 운영계정 실제 한도·심의 기간, 활용기간 만료일, Cloudflare 무료 배포 횟수 제한.
- **진행 시 오너가 할 일**
  1. 구조 결정: 추천안(서버 수집 + 정적 배포)으로 갈지 결정. 결정 후 구현은 별도 미션.
  2. data.go.kr 마이페이지에서 두 서비스의 **활용기간 만료일**과 오퍼레이션별 일일 트래픽 표기 확인.
  3. (권장, 일반 배포 전) 두 서비스 각각 **활용사례 등록 → 운영계정 신청**(요청 트래픽 10,000). 신청 자체는 오너 계정으로만 가능합니다.
  4. 수집용 키를 서버의 저장소 밖 파일에 둘지(지금 서버), 나중에 GitHub Actions 시크릿으로 옮길지 결정. 키 등록은 오너가 직접 하거나 별도 경로로 전달.
  5. 배포 저장소(`Dirtfy/chungyak-feed`, 공개) 생성 허락. 나중에 필요하면 Cloudflare 계정.
  6. 삭제 규칙(발표일 + 30일) 확정, 또는 다른 기간 지정.
