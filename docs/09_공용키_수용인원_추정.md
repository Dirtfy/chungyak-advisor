## 2. 사용자 1명의 하루 호출 수 (현재 앱 v0.5.1 코드 기준)
모든 data.go.kr 호출은 CheckWorker 한 곳에서만 나갑니다. 상세 화면과 경쟁률 화면은 기기 DB만 읽고, 위치 지도는 data.go.kr을 부르지 않습니다.
CheckWorker는 두 경우에 실행됩니다. 하나는 6시간 주기 백그라운드 실행(하루 4회)이고, 다른 하나는 '지금 확인' 버튼(누를 때마다 1회)입니다.

| 오퍼레이션 | 1회 실행당 | 평소(하루) | 성수기(하루) | 근거 |
|---|---|---|---|---|
| getAPTLttotPblancDetail (목록) | ⌈전국 30일 공고 ÷ 100⌉ = 1 | 4 + 수동 2 = **6** | 4 + 수동 10 = **14** | 지역 필터를 앱에서 함 → 전국 1페이지 |
| getAPTLttotPblancMdl (분양가) | 새 공고 수 | 13/30 ≈ **0.4** | ≈ **1** | 공고당 1회만(캐시). 첫 설치 때만 최대 20 |
| getAPTLttotPblancCmpet (경쟁률) | 접수~발표 사이 공고 수(3시간 간격) | 4건 × 4회 + 확정 0.4 ≈ **16** | 9건 × (4+수동 ~5) ≈ **45** | 접수~발표 약 9일 × 13건/30일 ≈ 4건 동시 |
| 합계 | | **약 23** | **약 60** | |

- 평소 = 수동 확인 하루 2회, 성수기 = 수동 10회 + 수도권 공고 월 30건으로 가정했습니다.
- 오류가 나면 30분부터 지수 백오프로 재시도합니다. 한도 초과(22)가 나면 모든 사용자가 동시에 재시도해 호출이 더 늘어납니다.

## 3. 수용 인원 계산
### 구조 A — 앱이 공용 키로 직접 호출
수용 인원 = 한도 ÷ (1인 하루 호출). 가장 먼저 차는 오퍼레이션(경쟁률)이 상한을 정합니다.

| | 목록 | 분양가 | 경쟁률(병목) | 한 통으로 합산될 경우 |
|---|---|---|---|---|
| 개발 40,000 평소 | 40,000÷6 = 6,666 | 40,000÷0.4 = 100,000 | **40,000÷16 ≈ 2,500 → 여유 두고 2,000** | 40,000÷23 ≈ 1,700 |
| 개발 40,000 성수기 | 40,000÷14 = 2,857 | 40,000 | **40,000÷45 ≈ 890** | 40,000÷60 ≈ 670 |
| 운영 100,000(가정) 평소 | 16,666 | — | **100,000÷16 ≈ 6,250 → 약 5,000** | 4,300 |
| 운영 100,000(가정) 성수기 | 7,140 | — | **100,000÷45 ≈ 2,200** | 1,670 |

- 신규 설치가 몰리는 날은 분양가 조회가 한 명당 최대 20회까지 듭니다. 이 경우 개발계정은 하루 신규 설치 2,000명이 한계입니다.
- 앱 코드를 최적화하면 수용 인원이 약 2배가 됩니다(경쟁률 조회를 하루 1~2회로 줄이고, 목록에 지역 조건을 넣는 방식).
- 비용: 0원. 운영 부담: 운영계정 심의, 키 교체 시 앱 업데이트 필요.
- 위험: 공개 저장소·APK에서 키를 추출할 수 있습니다. 악용이나 과호출이 생기면 전원이 먹통(22)이 되고, 초당 한도(23)는 수치조차 미공개입니다. 오너 방침("키는 앱에 넣지 않는다")과도 충돌합니다.

### 구조 B — 서버/캐시 하나가 받아서 배포
호출 수는 사용자 수와 무관하고, 수집 주기로만 정해집니다.
- 목록: 1시간마다 전국 1페이지 → 24/일
- 분양가: 새 공고(전국) 약 1/일
- 경쟁률: 전국 동시 진행 약 9건 × 3시간마다(8회) ≈ 72/일
- 합계 **약 100~110/일** — 개발계정 40,000의 0.3%라 운영계정 없이도 충분합니다.

사용자 쪽 상한은 배포 경로에서 정해집니다.

| 구성 | 비용 | 상한 |
|---|---|---|
| GitHub Actions(cron) + GitHub Pages 정적 JSON | 0원(공개 저장소) | Pages 권장 대역폭 100GB/월 ÷ (JSON 100KB × 하루 4회 × 30일) ≈ **8,300명**. ETag/304·압축이면 수만 명 |
| 같은 cron + Cloudflare Pages/R2 | 0원 | 송신 무과금 → **사실상 무제한** |
| 상시 서버(VPS) | 월 5~10천 원대 | 서버 사양만큼 |

- 키는 Actions 시크릿에만 둡니다. 저장소·APK에는 들어가지 않습니다.
- 사용자는 정적 파일을 GET으로 받기만 하므로 개인정보 전송이 없습니다. 자격 판정은 지금처럼 기기 안에서 합니다.
- 운영 부담: cron 실패 감시, 키 활용기간 만료 시 연장(개발계정 보통 2년, 가정), "서버 없는 앱" 구조를 일부 변경. 데이터는 '이용허락범위 제한 없음'이라 재배포 가능합니다.

## 4. 권장안
1. **구조 B**를 권장합니다: GitHub Actions 수집 + 정적 JSON. 개발계정 그대로 쓰고, 운영계정 신청은 필요 없습니다. 0원이며, 앱은 "공용 피드 기본 + 개인 키 선택(백업 경로)"으로 바꿉니다.
2. 구조 A는 한도(약 900~2,000명)보다 키 노출 위험 때문에 비추천합니다.
3. 결정 전에 오너님이 data.go.kr 마이페이지 → 활용신청 상세에서 오퍼레이션별 '일일 트래픽' 표기를 확인해 주시면 가정 하나가 확인으로 바뀝니다.
